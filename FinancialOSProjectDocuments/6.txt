
# Chapter 2 — Conceptual Domain Model

---

## Introduction

The Conceptual Domain Model defines the major concepts within FinancialOS and the relationships between them.

It intentionally avoids implementation details.

There are no classes.

No inheritance.

No databases.

No APIs.

Instead, this model describes the conceptual structure of financial reality as understood by FinancialOS.

Every software component should ultimately implement this model rather than redefine it.

---

# The FinancialOS Universe

I think everything belongs in one of **five domains**.

```text
                Financial Reality
                       │
 ┌─────────────┬────────┴─────────┬────────────┐
 │             │                  │            │
Evidence   Knowledge         Decisions     Stewardship
 │             │                  │            │
 └─────────────┴──────────────────┴────────────┘
                    Time
```

Notice something interesting.

**Time surrounds everything.**

Nothing exists outside of time.

---

# Domain 1 — Financial Reality

Financial Reality represents things that actually happened.

Examples:

* A paycheck was deposited.
* A mortgage payment occurred.
* A receipt exists.
* Interest accrued.
* A dividend was paid.

Reality exists whether or not FinancialOS ever sees it.

The software does not create reality.

It discovers it.

---

# Domain 2 — Evidence

Evidence is how reality enters the system.

Examples

```text
Receipt

Bank Statement

CSV

OFX

PDF

Image

API

Email

Manual Entry
```

Evidence answers:

> **How do we know?**

Evidence should be immutable.

---

# Domain 3 — Knowledge

Knowledge is where FinancialOS begins creating understanding.

Knowledge includes

```text
Merchant

Category

Subscription

Recurring Payment

Transfer

Income

Investment

Relationships

Confidence

Provenance
```

Knowledge is always derived from evidence.

Knowledge becomes richer over time.

---

# Domain 4 — Decisions

Knowledge exists for one reason.

To support decisions.

Examples

```text
Budget Allocation

Goal

Forecast

Recommendation

Scenario

Plan

Reminder
```

Notice budgets finally appear.

Budgets are decision-support objects.

Not financial facts.

This is a huge architectural distinction.

---

# Domain 5 — Stewardship

This is the destination.

Stewardship contains

```text
Habits

Progress

Growth

Financial Story

Achievements

Life Events

Reflection

Legacy
```

Nothing here is transactional.

Everything here is longitudinal.

# Here's the breakthrough

I think we've been using the word **FinancialRecord** too broadly.

I would actually split it into two concepts.

## Financial Event

A thing that happened.

Example

```text
Debit Card Purchase

Paycheck

Mortgage Payment

Dividend

Transfer

ATM Withdrawal
```

---

## Financial Record

The platform's representation of that event.

```text
Financial Event

↓

Evidence

↓

Financial Record
```

Why?

Because the event existed before we observed it.

The record is our representation.

That's a very DDD way of thinking.

---

# Another concept I think we're missing

Every event has **Actors**.

Not just people.

Actors.

Examples

```text
Person

Family

Employer

Bank

Merchant

Government

Utility Company

Investment Firm
```

Suddenly we can ask

> Who participated?

instead of

> Which account?

That becomes incredibly powerful.

---

# Another concept

Resources.

Money isn't the only resource.

Eventually we may support

* Reward points
* Airline miles
* Gift cards
* Store credit
* HSA balances
* PTO balances
* Cryptocurrency
* Stock options

Those are all resources.

Maybe someday carbon credits.

Maybe time.

Maybe volunteer hours.

By modeling **resources** instead of only money, FinancialOS becomes extensible without changing its philosophy.

---

# I think we've discovered the "kernel"

Operating systems have kernels.

I think FinancialOS does too.

Not code.

Concepts.

```text
Reality

Evidence

Record

Knowledge

Decision

Outcome
```

Everything else builds on those six ideas.

If we protect those six concepts, the platform can evolve almost indefinitely.

# Architect's Reflection

This chapter changed my own mental model of the platform.

When we started, I imagined FinancialOS as a budgeting system with a strong domain model. Now I think it's something more fundamental: a **knowledge system about financial reality**.

That shift has an important consequence. I no longer believe our primary aggregate root should simply be `FinancialRecord`. Instead, I think our primary responsibility is to preserve the chain from **Reality → Evidence → Record → Knowledge** without ever breaking it.

I'd also like to propose one more adjustment before we continue.

I think we've been using **Knowledge** to describe several different things:

* normalized facts (merchant, account, payee),
* classifications (category, recurring, transfer),
* analytics (observations, patterns),
* and guidance (insights, recommendations).

Those are different kinds of knowledge.

In the next chapter, I want us to define a **Knowledge Taxonomy** before we define the ubiquitous language. I suspect that once we classify the different kinds of knowledge, the entities and aggregates will become dramatically clearer.

## One strategic suggestion

I'd like to introduce one rule that we follow for the rest of the architecture:

> **Every entity must be able to answer one question.**

For example:

| Entity           | Primary Question                        |
| ---------------- | --------------------------------------- |
| Evidence         | *How do we know this happened?*         |
| Financial Event  | *What actually happened?*               |
| Financial Record | *How does FinancialOS represent it?*    |
| Merchant         | *Who received or sent value?*           |
| Observation      | *What did we notice?*                   |
| Pattern          | *What repeats?*                         |
| Insight          | *Why does it matter?*                   |
| Recommendation   | *What should be done?*                  |
| Decision         | *What did the user choose?*             |
| Outcome          | *What happened because of that choice?* |

That single-question discipline will keep every future entity focused and prevent the domain from becoming bloated. I have a feeling it's going to become one of the most useful design techniques we use as we build FinancialOS.
